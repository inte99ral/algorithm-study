## 개요

&nbsp; 코딩 컨벤션(Coding Conventions)은 코드 작성시 약속된 규칙을 말합니다. 함수명이나 프로젝트 구조 등 개발하는 형식에 대한 규칙을 관습화하여 코드 구조의 일관성을 유지하고 직관적인 이해를 돕습니다.

## 네이밍

### 일반적 원칙

-   모든 경우에 공백은 절대적으로 사용하지 않는 것이 좋습니다

-   <u><b>프로젝트 최상단 루트 폴더명</b></u>은 소문자와 하이픈만 사용한 `케밥 케이스` 를 따릅니다.
    
    &nbsp; 프로젝트의 최상단 루트 폴더명은 내 컴퓨터의 운영체제, Git, 클라우드 서버(Linux), 그리고 빌드 도구가 직접 마주하는 이름입니다. 모든 경우에서 충돌을 피해야하기 위하여 띄어쓰기를 포함한 모든 특수문자 체크 상황과 대소문자 비교상황을 배제해야 합니다.

-   <u><b>소스 코드 내부 파일</b></u>은 대소문자를 사용하는 `파스칼 케이스` 를 사용해도 됩니다.
    
    &nbsp; 개발 프로젝트 폴더 안에서는 컴파일러/인터프리터'의 영역입니다. 특수문자와 띄어쓰기를 사용하지 않았다면 충돌 이슈는 없으며 프로그래밍 언어의 문법과 개발자의 생산성이 중요합니다. 코드 구조 직관성을 위하여 React, Vue, 혹은 Unity(C#) 같은 현대적인 개발 환경에서는 "컴포넌트나 클래스의 이름은 무조건 대문자로 시작해야 한다(PascalCase)"는 문법적 규칙이나 강력한 관례가 있습니다.

#### Semantic Versioning：유의적 버전 명세

```txt
program_v3.3.3_windows_x64.zip
```

-   [참고 링크](https://velog.io/@i33w/semver)

Semantic Versioning 은 소프트웨어 서비스 간에 의존성 문제를 조정하기 위하여 GitHub의 공동 설립자인 Tom Preston-Werner가 제안한 방식입니다.

Semantic Versioning은 버전 번호를 어떻게 정하고 올려야 하는지를 명시하는 규칙입니다.

-   3 번호 표기

    한 개발 패키지의 버전을 `.` 으로 구분하여 세 부분으로 나눠 표기합니다.

    <div align="center">
    `『MAJOR_NUMBER』.『MINOR_NUMBER』.『PATCH_NUMBER』`
    </div>

    -   전 버전과 호환되지 않게 API가 바뀌면 주(主) major 버전을 한 단계 올립니다.
    -   전 버전과 호환되면서 새로운 기능이 추가되었다면 부(部) minor 버전을 한 단계 올립니다.
    -   전 버전과 호환되면서 문제점만 개선한 것이라면 수(修) patch 버전을 한 단계 올립니다.

-   4 번호 표기

    네 부분으로 구분했을 경우에는 맨 끝에 빌드번호를 붙인 경우 입니다.

    <div align="center">
    `『MAJOR_NUMBER』.『MINOR_NUMBER』.『PATCH_NUMBER』.『BUILD_NUMBER』`
    </div>

    -   빌드 번호는 배포나 수정사항의 순번 등 추가 정보를 제공합니다.
    -   패치라고 불릴 만한 사항은 없으나 라이브러리의 변화나 API 관련으로 재빌드 사항이 있었을 경우, 또는 테스트 빌드 버전이 분리되어 있을 경우에 명시합니다.

-   추가 표기

    빌드 타겟인 OS 와 CPU 아키텍쳐 종류를 기입할 땐 그 뒤에 작성합니다.

    <div align="center">
    `『MAJOR_NUMBER』.『MINOR_NUMBER』.『PATCH_NUMBER』_『OS_TYPE』_『CPU_ARCHITECTURE_TYPE』`
    </div>

### C++

역사가 길고, 수많은 사용자들이 사용하던 언어이기 때문에 여러 네이밍 컨벤션이 존재합니다.

#### MS C# 호환성 스타일

-   장점:
    -   세련되었습니다.
    -   거의 C# 이나 최신언어 규칙 그대로 따라갑니다. 포팅 시 시인성도 높고 상호호환성도 높습니다.
-   단점:
    -   딱히 철학적인 부분은 없는 설계입니다. 그냥 이쁘고 시인성 높아서 쓰는 겁니다.

-   이 스타일은 다음의 작명 법칙을 따릅니다.

    -   <u><b>파일</b></u>: `FileName.cpp`, 파스칼 케이스를 따릅니다.
    -   <u><b>클래스/구조체</b></u>: `class ClassName{}`, 파스칼 케이스를 따릅니다.
    -   <u><b>메서드</b></u>: `ClassName.MethodName(x,y)`, 파스칼 케이스를 따릅니다.
    -   <u><b>인스턴스와 변수</b></u>: `valueName`, 카멜 케이스를 따릅니다.
    -   <u><b>비공개/멤버변수</b></u>: `_privateValue` 언더바 + 카멜 케이스를 따릅니다.
    -   <u><b>상수</b></u>: `CONSTANT_NAME` 스크리밍 스네이크 케이스를 따릅니다.

#### 에픽게임즈 모던 스타일

-   장점:
    -   **직관성과 현대성**: C# 이나 자바 등 최신 객체지향 언어들의 작명 원칙을 C++ 에 반영하여 매우 세련되었으며 시인성이 높습니다.
    -   **생산성**: IDE(VS Code, Visual Studio 등)의 발달로 대소문자 기반의 코드 자동 완성이 완벽히 지원되므로 개발 생산성이 좋습니다.

-   단점:
    -   **생태계 간의 이질감**: C++ 표준 라이브러리(STL) 및 대다수의 오픈소스 라이브러리는 소문자 스네이크 케이스(`std::vector`, `std::string`)를 사용하므로, 내가 짠 코드(`MyVariable`)와 표준 코드가 한 줄에 섞일 때 이질감이 발생합니다.
    -   **크로스 플랫폼 빌드 리스크**: Windows OS 환경은 파일명의 대소문자를 구분하지 않지만(Case-Insensitive), Linux OS 환경은 엄격하게 구분합니다(Case-Sensitive). Windows에서 실수로 파일명 대소문자를 틀리게 `#include` 하더라도 빌드가 성공하기 때문에, 이를 Linux 서버로 가져갔을 때 뒤늦게 빌드가 터지는 참사가 발생할 수 있습니다.

-   이 스타일은 다음의 작명 법칙을 따릅니다.

-   <u><b>파일</b></u>: `FileName.cpp`, 파스칼 케이스를 따릅니다.
    -   <u><b>클래스/구조체</b></u>: `class ClassName{}`, 파스칼 케이스를 따릅니다. (언리얼 엔진의 경우 `AActor`, `UObject`, `FVector` 처럼 고유 접두사를 붙입니다.)
    -   <u><b>메서드</b></u>: `MethodName()`, 파스칼 케이스를 따릅니다.
    -   <u><b>인스턴스와 변수</b></u>: `ValueName` 지역변수도 파스칼 케이스를 권장합니다.
    -   <u><b>비공개/멤버 변수</b></u>: `bPrivateValueName` 자료형접두사 + 파스칼케이스를 사용합니다.
    -   <u><b>상수</b></u>: `kConstantName` k + 파스칼케이스를 따릅니다.

#### 구글 가이드라인 스타일

-   장점:
    -   **최고의 플랫폼 안정성**: 파일명만큼은 안전하게 전체 소문자와 언더바(`_`)만 사용하므로, 어떤 구형 OS나 빌드 시스템(Makefile 등), 크로스 플랫폼 환경(Linux/Windows) 간의 이식에서도 대소문자 문제나 파싱 오류를 원천 차단합니다.
    -   **STL 표준과의 비주얼적 조화**: 가장 많이 작성하게 되는 변수명에 소문자 스네이크 케이스를 사용하므로, C++ 표준 라이브러리 타입(`std::string`) 및 함수들과 시각적으로 완벽하게 어우러집니다.
    -   **역할의 시각적 분리**: 클래스/함수(`PascalCase`)와 변수(`snake_case`)의 형태가 완전히 다르기 때문에, 코드만 봐도 이것이 타입인지 인스턴스 변수인지 뇌를 거치지 않고 직관적으로 파악됩니다.

-   단점:
    -   **하나의 코드, 다채로운 규칙**: 하나의 대상(클래스, 파일, 변수)이 개념적으로는 같음에도 불구하고 클래스는 `ClassName`, 파일은 `class_name.cc`, 변수는 `class_name` 처럼 각기 다른 규칙이 적용되어 타 언어 개발자나 입문자에게는 규칙이 복잡하고 난독을 유발할 수 있습니다.
    -   **타 언어와의 이질성**: 현대 대다수의 메인스트림 언어(C#, Java, TS 등)가 변수에는 카멜 케이스를, 상수에는 대문자 스네이크 케이스(`MAX_INT`)를 쓰는 반면, 구글 C++은 상수에 `kConstantName`을 쓰는 등 독자적인 규칙을 고수하여 멀티 언어를 다루는 개발자에게 혼동을 줍니다.

-   이 스타일은 다음의 작명 법칙을 따릅니다.
    -   <u><b>파일</b></u>: `file_name.cpp`, 스네이크 케이스를 따릅니다.
    -   <u><b>클래스/구조체</b></u>: `class ClassName{}`, 파스칼 케이스를 따릅니다.
    -   <u><b>메서드</b></u>: `MethodName()`, 파스칼 케이스를 따릅니다.
    -   <u><b>인스턴스와 변수</b></u>: `value_name`, 스네이크 케이스를 따릅니다.
    -   <u><b>비공개/멤버 변수</b></u>: `variable_name_`, 소문자 스네이크 케이스를 쓰되 뒤에 언더바를 붙입니다.
    -   <u><b>상수</b></u>: `kConstantName`, 접두사 k + 파스칼 케이스를 따릅니다.(헝가리안 표기법)

#### C++ STL 라이브러리 스타일

-   특징:
    -   거의 소문자 스네이크 케이스만 쓰는 스타일입니다.

-   장점:
    -   완벽한 언어적 일관성: C++ 표준 라이브러리(std::vector, std::string, std::unique_ptr)와 완벽하게 똑같은 문법적 형태를 가집니다. 내가 짠 코드와 언어 자체의 내장 기능이 한 몸처럼 부드럽게 어우러집니다.

    -   플랫폼 독립성: 구글 스타일과 마찬가지로 파일명과 식별자 전체에 소문자와 언더바만 사용하므로, 전 세계 어떤 OS, 어떤 구형 컴파일러나 빌드 도구 체인을 만나도 대소문자 문제로 빌드가 터질 일이 없습니다.

-   단점:
    -   역할 구분의 모호함: 클래스(타입), 메서드(함수), 변수, 상수가 전부 소문자 스네이크 케이스로 똑같이 생겼습니다. 코드 가독성 측면에서 해당 식별자가 클래스인지, 인스턴스 변수인지, 함수인지 문맥을 보거나 툴의 도움(마우스 오버) 없이 단번에 파악하기 어렵습니다.
    -   작성 피로도: 단어마다 언더바(_)를 계속 눌러야 하므로 타이핑 효율이 떨어지고, 모던 객체지향 언어(C#, Java 등)에 익숙한 개발자들에게는 심한 이질감과 투박함을 줍니다.

-   이 스타일은 다음의 작명 법칙을 따릅니다.
    -   <u><b>파일</b></u>: `file_name.cpp`, 소문자 스네이크 케이스를 따릅니다.
    -   <u><b>클래스/구조체</b></u>: `class class_name{}`, 소문자 스네이크 케이스를 따릅니다.
    -   <u><b>메서드/함수</b></u>: `method_name()`, 소문자 스네이크 케이스를 따릅니다.
    -   <u><b>인스턴스/변수</b></u>: `value_name`, 소문자 스네이크 케이스를 따릅니다.
    -   <u><b>비공개/멤버 변수</b></u>: `_variable_name`, 부스트(Boost) 스타일을 따를 경우 구글과 반대로 앞에 언더바를 붙여 _member_value 형태로 씁니다.
    -   <u><b>상수</b></u>: `constant_name`, 소문자 스네이크 케이스를 따릅니다.

#### C 레거시 프로젝트 스타일

-   장점:
    -   강력한 타입 직관성 (헝가리안): 변수명 앞에 타입 정보(포인터는 p, 정수는 n 등)를 접두사로 붙이기 때문에, 툴의 도움(마우스 오버)이 전혀 없는 구형 텍스트 에디터나 메모장으로 코드를 봐도 변수의 데이터 타입을 단번에 알 수 있습니다.
    -   확실한 상수 강조: 상수를 MAX_BUFFER_SIZE처럼 대문자 스네이크 케이스로 박아놓기 때문에, 코드 흐름 내에서 '절대 변하지 않는 고정 리터럴'의 존재감이 압도적으로 눈에 띕니다.

-   단점:
    -   유지보수의 지옥: 만약 개발 중에 변수의 데이터 타입을 int에서 double이나 float로 변경하게 되면, 그 변수가 쓰인 모든 곳의 변수 이름(접두사)을 일일이 수정해야 하는 대참사가 발생합니다.
    -   극악의 가독성과 지저분함: 변수명 앞에 온갖 알파벳 접두사가 주렁주렁 달리면서(lpstrName, uiCount) 코드가 매우 지저분해지고 읽기 힘들어집니다. 현대에는 IDE(개발 툴)가 타입을 다 알려주기 때문에 완전히 '과거의 유산(Anti-pattern)' 취급을 받습니다.

-   이 스타일은 다음의 작명 법칙을 따릅니다.
    -   <u><b>파일</b></u>: `main.c, utils.h`, 소문자 스네이크 케이스를 쓰거나 아예 단어를 축약하여 짧게 씁니다.
    -   <u><b>구조체</b></u>: `typedef struct tagMyStruct {} MYSTRUCT;`, 구조체 태그와 typedef 선언을 혼용하며 대문자나 파스칼 케이스를 씁니다.
    -   <u><b>함수</b></u>: `GetSystemTime()` 또는 `pthread_create()`, 윈도우 진영은 파스칼, 유닉스 진영은 소문자 스네이크를 사용합니다.
